Ports & Sockets

A port number alone doesn't identify a conversation. It takes the full combination, a socket, to tell two connections to the exact same service apart.

What a port actually is

An IP (Internet Protocol) address gets a segment to the right host. A port number, a 16-bit field in both the TCP and UDP headers, gets it to the right application on that host. Without ports, a single host could only ever run one network application at a time, since there'd be no way to tell a web server's traffic from a DNS (Domain Name System) resolver's.

A socket is what actually identifies a conversation

An IP address is a building's street address. A port number is the apartment inside that building mail is headed for. But if you're expecting several different replies from the same apartment, one for a package, one for a bill, just knowing the apartment number isn't enough to sort your own incoming mail. A socket is the full pairing stapled to every exchange: which address and apartment it came from, which address and apartment it's going to, and which protocol it's using. Formally, it's a five-part combination: protocol, source IP, source port, destination IP, destination port. Change any one of those five, and it's a different socket, a completely distinct connection, even if everything else about it is identical.

WHY YOUR OS PICKS A RANDOM SOURCE PORT FOR OUTGOING CONNECTIONS

Every time an application opens an outgoing connection, the OS assigns it an unused port from the ephemeral range, exactly so the situation above works: the OS itself is what keeps every simultaneous outgoing connection from the same host distinct. This is also the exact mechanism PAT depends on, rewriting each internal host's chosen source port to a unique public one so replies for every device come back to the right place.
