BGP Basics

Every protocol so far in this module routes traffic inside one organization's network. BGP is what routes traffic between organizations, which is to say, it's what the actual internet runs on.

Autonomous Systems: The internet's real "networks"

OSPF (Open Shortest Path First) and EIGRP (Enhanced Interior Gateway Routing Protocol) assume one administrator controls the whole topology. The internet is the opposite: thousands of independently-operated networks, each one an Autonomous System (AS), identified by an AS number, that has to agree to exchange traffic with its neighbors without any single authority dictating the whole map. BGP (Border Gateway Protocol) is the protocol those ASes use to tell each other what they can reach.

It's less like a road network inside one city, and more like national airlines negotiating bilateral agreements about which routes they'll fly between each other's countries. Every relationship is its own negotiated agreement, not a single global authority assigning routes.

eBGP vs. iBGP

  • eBGP (external): a session between routers in different ASes. This is the actual internet-facing peering or transit relationship.
  • iBGP (internal): a session between routers inside the same AS, used to make sure everything learned from the outside world gets distributed consistently throughout that AS's own network.

"Best" isn't just "shortest"

Interior protocols like OSPF pick the lowest-cost path, full stop. BGP is different on purpose: it's as much a policy and business tool as a technical one, since real transit and peering relationships involve contracts, cost, and trust, not just distance. Instead of a simple metric, BGP compares a whole ordered list of path attributes, and it works through them in a fixed order, stopping at the first one that produces a single winner.

The path attributes, and where each one lives

Not every attribute travels the same distance. Some never leave the router they're configured on; others cross AS boundaries and get compared against everyone else's:

AttributeWhere it's exchangedWins withWhat it's for
WEIGHTLocal to one router only, never advertised at allHigherA quick, router-specific override with zero blast radius elsewhere
LOCAL_PREFiBGP only, inside your own ASHigherMaking every router in your AS agree on which exit point to prefer for outbound traffic
AS-PATHEverywhere, eBGP and iBGPShorterLoop prevention (reject any path that already contains your own AS) and a rough distance signal
ORIGINEverywhereIGP over EGP over IncompleteHow the route first entered BGP; rarely the deciding factor today
MEDSent to eBGP neighbors, compared only within routes from the same neighboring ASLowerA hint to a neighboring AS about which of your entry points you'd prefer they use
NEXT_HOPEverywhere; rewritten by eBGP, normally left alone by iBGPN/AThe actual IP address traffic gets forwarded toward next

LOCAL_PREF only ever matters inside your own AS, since it's an iBGP-only attribute your own routers use to agree with each other. MED is the opposite kind of local: it only gets compared between routes offered by the same neighboring AS, so it can't override a shorter path from a completely different neighbor.

The order BGP actually checks them in

Real implementations vary slightly, but the practical order is close to this, and it's evaluated top to bottom until one candidate route is left standing:

  1. Highest WEIGHT
  2. Highest LOCAL_PREF
  3. Prefer a locally originated route
  4. Shortest AS-PATH
  5. Lowest ORIGIN type
  6. Lowest MED (same neighboring AS only)
  7. Prefer eBGP-learned over iBGP-learned
  8. Lowest IGP metric to reach NEXT_HOP

That order is why the common assumption "BGP always picks the shortest AS-PATH" is wrong: LOCAL_PREF is checked first, so a network engineer can deliberately override a shorter external path just by configuring a higher LOCAL_PREF on the longer one.

WHY THIS ISN'T "JUST A BIGGER OSPF"

An enterprise network can safely trust every router in it, because one team controls all of them. The internet can't make that assumption at all. BGP's entire design (policy-based path selection, explicit peering agreements) exists because every AS boundary is also a trust boundary.
