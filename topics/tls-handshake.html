TLS/SSL Handshake (1.2 vs 1.3)

How a client and server that have never spoken before agree on a shared secret entirely in the open, before a single byte of actual data is encrypted.

What the handshake has to accomplish

Meeting a new business contact for the first time means checking their credentials, agreeing on which shared rules you'll both follow, and settling on a private code only the two of you know before discussing anything sensitive. TLS (Transport Layer Security) does exactly that, in three jobs: agree on a protocol version and cipher suite, authenticate the server using the certificate chain from PKI & Digital Certificates, and establish shared symmetric session keys. That last part is hybrid encryption in action: asymmetric crypto is used only to set the session keys up, then fast symmetric encryption handles the actual data for the rest of the connection.

TLS 1.2: Two round trips

A full TLS 1.2 handshake needs two full round trips between client and server before any application data can be sent: one to agree on parameters and receive the server's certificate, a second to actually exchange the key material and confirm both sides derived the same session keys.

How the session keys actually get derived math, not wire bytes

Nothing sent so far is the actual encryption key. Both sides separately compute it from what was exchanged, and never transmit it.

1. Pre-Master SecretBoth sides combine their own private key with the other side's public key (Diffie-Hellman). Same math, same result on both ends, without either one ever sending the secret itself
2. Master SecretA 48-byte value derived by repeatedly running HMAC-SHA256 over the pre-master secret, the literal string "master secret", and both randoms
3. Key expansionThe master secret is stretched the same way into six separate keys: a MAC key and a write key for each direction, plus an IV for each

TLS 1.3: One round trip, sometimes zero

TLS 1.3 cuts this down by having the client guess which key exchange method the server will accept and send its key share immediately in the ClientHello, instead of waiting to be told. If the guess is right, the whole handshake collapses into a single round trip.

What's actually on the wire, message by message

ClientHello client → server, plaintext
Cipher SuitesA much shorter list, every option now an AEAD (Authenticated Encryption with Associated Data) cipher, e.g. TLS_AES_128_GCM_SHA256, TLS_CHACHA20_POLY1305_SHA256
key_shareThe new part: the client's own ephemeral Diffie-Hellman public key, sent immediately, guessing which group the server will accept
supported_versionsExplicitly states TLS 1.3, since the version field itself still says 1.2 for compatibility with old middleboxes that choke on an unrecognized version
ServerHello server → client, plaintext, the last unencrypted message
key_shareThe server's own ephemeral public key for the group it picked. The moment both sides have this, they can both compute the handshake keys
Cipher SuiteThe one chosen suite
EncryptedExtensions, Certificate, CertificateVerify, Finished server → client, encrypted

Everything from here on is encrypted with handshake keys derived right after ServerHello. Four messages the server used to send as a separate, later flight in TLS 1.2 are now sent together, and hidden from anyone just watching the wire.

EncryptedExtensionsExtensions that don't need to be public, now that encryption is already active
CertificateThe server's certificate chain, same as before, just now encrypted
CertificateVerifyA signature, made with the certificate's own private key, over everything exchanged so far. This is new: TLS 1.2 never proved the server holds that key this directly
FinishedProof the server derived the right keys, the same role it played in TLS 1.2
Finished client → server, encrypted

The client's own proof. The moment the server verifies it, application data flows freely in both directions, and both sides derive a completely separate set of application traffic keys from the ones that encrypted the handshake itself.

0-RTT early data optional, only on a resumed connection

If the client already holds a PSK (Pre-Shared Key) from a previous connection's session ticket, it can attach encrypted application data directly to its very first ClientHello, before the server has replied at all. That's what "0-RTT" means: zero extra round trips beyond just sending the request. The trade-off is that this early data has no forward secrecy yet and can be replayed by an attacker who captured it, so servers typically only accept it for requests that are safe to repeat, like a GET, never for anything that changes state.

WHY THIS SITS ON TOP OF TCP, NOT INSTEAD OF IT

TLS still assumes a reliable, ordered byte stream underneath it, which is exactly what TCP provides. That's true for TLS 1.2 and 1.3 alike. QUIC, the transport HTTP/3 uses (see HTTP/HTTPS: 1.1 vs 2 vs 3), handles this differently by folding TLS 1.3 directly into its own transport instead of layering it on top of TCP.
