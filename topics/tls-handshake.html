TLS/SSL Handshake (1.2 vs 1.3)

How a client and server that have never spoken before agree on a shared secret entirely in the open, before a single byte of actual data is encrypted.

What the handshake has to accomplish

Meeting a new business contact for the first time means checking their credentials, agreeing on which shared rules you'll both follow, and settling on a private code only the two of you know before discussing anything sensitive. TLS (Transport Layer Security) does exactly that, in three jobs: agree on a protocol version and cipher suite, authenticate the server using the certificate chain from PKI & Digital Certificates, and establish shared symmetric session keys. That last part is hybrid encryption in action: asymmetric crypto is used only to set the session keys up, then fast symmetric encryption handles the actual data for the rest of the connection.

TLS 1.2: Two round trips

A full TLS 1.2 handshake needs two full round trips between client and server before any application data can be sent: one to agree on parameters and receive the server's certificate, a second to actually exchange the key material and confirm both sides derived the same session keys.

TLS 1.3: One round trip, sometimes zero

TLS 1.3 cuts this down by having the client guess which key exchange method the server will accept and send its key share immediately in the ClientHello, instead of waiting to be told. If the guess is right, the whole handshake collapses into a single round trip.

Round trips before dataTwoOne (zero with session resumption)

WHY THIS SITS ON TOP OF TCP, NOT INSTEAD OF IT

TLS still assumes a reliable, ordered byte stream underneath it, which is exactly what TCP provides. That's true for TLS 1.2 and 1.3 alike. QUIC, the transport HTTP/3 uses (see HTTP/HTTPS: 1.1 vs 2 vs 3), handles this differently by folding TLS 1.3 directly into its own transport instead of layering it on top of TCP.
